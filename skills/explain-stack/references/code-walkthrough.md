# Code walkthrough

Goal: the user understands the **most important code** in their project (the lines that make it work, and any algorithms) well enough to change it and explain it in an interview. You explain; you never rewrite.

## 1. Pick what to explain

**Targeted** (`/explain-stack code <path or function name>`): Glob/Grep for it. Explain that file or function. For a big file, explain its 2–4 most important functions and list the rest in one line each.

**Automatic** (`/explain-stack code`): choose **3–5 pieces** of code, 5–40 lines each. Rank by:
1. **Core logic:** the code that does what the project is *for* (e.g. the scoring in a quiz app, the price calculation in a shop, the scheduling in a spaced-repetition app).
2. **Algorithms and data processing:** sorting, searching, ranking, scheduling, recursion, pagination, parsing, matching, retries/backoff, caching, rate limiting, math formulas, state machines.
3. **Critical paths:** the auth/login flow, the payment flow, the main request handler, data writes.
4. **Tricky lines:** regex, bit operations, clever one-liners, `reduce` chains, list comprehensions, async/concurrency, SQL queries, date/time math.

How to find them quickly (with Grep, always excluding `!**/.env*`):
- Start from the entry point and the README's main feature, and follow the main action.
- Grep for algorithm signals: `sort`, `reduce`, `while`, `recursive`, `score`, `rank`, `interval`, `retry`, `backoff`, `cache`, `hash`, `Math.`, `random`, `schedule`, `queue`, `parse`, `regex`/`re.`, `async`/`await`/`Promise.all`.
- Prefer code the user's project wrote, not config, generated files, migrations or vendored code. Skip tests unless they explain the logic best.
- Budget: about 10–15 file reads.

If the project has no real algorithm (a plain CRUD app), say so honestly. Then explain the main request flow and the trickiest lines instead.

## 2. Card for each piece of code

```
### <N>. <Plain-language name>: `<path>:<start>-<end>` (`<function name>`)
**What it does:** <one sentence a beginner understands>
**Algorithm / pattern:** <real name if there is one (e.g. "SM-2 spaced repetition", "binary search", "debounce", "exponential backoff", "memoization"), or "no named algorithm: <what kind of logic it is>">

<the code, quoted exactly, ≤15 lines; if longer, quote the key part and say "(lines X–Y skipped: …)">

**Line by line:**
- `L<n>` <what this line does and WHY it's needed>
- …(only the lines that matter; group trivial ones)

**Example run:** <trace it with one concrete input, step by step, showing values changing>
**Speed (Big-O):** <only if it matters: "O(n): it looks at each card once", in plain words; say when it would get slow>
**Edge cases:** <1–3: empty input, null, duplicates, huge numbers, time zones, concurrent requests; say whether the code handles them, with the line>
**In an interview, say:** "<2–3 first-person sentences explaining this code>"
```

Rules:
- **Quote real code exactly**, with correct line numbers from the file **as it is now**: re-read it right before quoting, never from memory or an old `CODE.md`. Never paraphrase code as if it were a quote.
- **Explain the *why*, not only the *what*.** "`L14` sorts by due date *so that* the most overdue card is shown first" beats "`L14` sorts the list".
- **Trace with real values.** A worked example teaches more than any description. Use small, concrete inputs (e.g. `ease=2.5, interval=6 → next interval 15 days`).
- **Name the concept** a beginner should google ("this is called *memoization*"), and explain it in one sentence.
- Beginner level: explain syntax that might be new (`?.`, `??`, destructuring, comprehensions, decorators) the first time it appears. Advanced level: skip syntax, focus on design, complexity and alternatives.
- **Bugs and risks:** if you see a likely bug (off-by-one, missing `await`, unhandled empty list), mention it as a learning point with the line number. Never fix it.

## 3. Check understanding

Ask **3 short questions, one at a time** (the user can type `skip`):
- **Predict the output:** "What does `nextInterval(1, 2.5)` return?"
- **What if:** "What happens if `cards` is empty on line 22?"
- **Why:** "Why is the list sorted *before* slicing on line 30?"
After each answer: 1–2 sentences of feedback and the correct answer.

## 4. Save

Ask once whether to save the walkthrough. If yes, write `CODE.md` in the project root with a short intro, the cards, the quiz with answers, and the footer:
`*Generated by [explain-stack](https://github.com/Aleksa5000/explain-stack) on <YYYY-MM-DD>. Explanations are based on the code at that time.*`
If `CODE.md` exists without that footer, ask before overwriting and offer `docs/CODE.md` or `CODE.explained.md` instead.
